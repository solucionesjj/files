# ADR-0002 — PostgreSQL 18 as the single source of truth (UUIDv7, SQL migrations)

- **Status:** Accepted
- **Date:** 2026-10-23
- **Deciders:** Architecture, Data

## Context

File metadata, ownership, links, retention schedules, audit, and idempotency all need
transactional integrity. The source mandates PostgreSQL 18 LTS. We need non-guessable,
index-friendly IDs and a migration strategy that works for both the .NET app and local/CI.

## Decision

- PostgreSQL 18 is the only operational datastore (no Redis/queue in v1; Redis is a future
  option for rate limits).
- Primary keys are `uuid` generated by PostgreSQL 18's `uuidv7()` (time-ordered). Application
  code may also generate UUIDv7 (same ordering guarantee) when it needs the ID before insert.
- DDL is managed with **Flyway SQL migrations** in `db/migrations/` (`V1__...`, `V2__...`).
  EF Core maps the schema but does **not** own migrations.
- Enumerations are `text` + `CHECK` constraints; timestamps are `timestamptz` (UTC); identifiers
  use snake_case in the DB and PascalCase in C# (Npgsql naming convention).
- Search uses `pg_trgm` + `ILIKE`; no external search engine in v1.

## Consequences

- One transactional boundary for file state, link reservations, outbox, and audit.
- Flyway can run in CI, local Docker, and a pre-deploy step on the host; rollback is forward-fix, using
  expand/contract for breaking changes (see deployment doc).
- EF model drift must be detected by integration tests; DDL changes require updating both the SQL
  and the mapping.
- UUIDv7 leaks creation time (acceptable; creation time is already exposed) and improves index
  locality over UUIDv4.

## Alternatives considered

- EF Core migrations as the source of truth: rejected to keep a language-neutral, reviewable DDL
  artifact and support Flyway in compose/CI.
- BIGSERIAL identity: rejected (leaks counts, harder to expose safely).
- UUIDv4: rejected (index fragmentation, no ordering).
- Separate search engine: rejected for scale reasons; revisit beyond ~1M files.
