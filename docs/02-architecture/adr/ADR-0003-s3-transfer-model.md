# ADR-0003 — Direct-to-S3 multipart uploads, API-proxied downloads

- **Status:** Accepted
- **Date:** 2026-10-23
- **Deciders:** Architecture, Security

## Context

Files must support up to 5 GiB objects, keep the bucket private, avoid overwrites, verify uploads,
count only completed downloads, and never expose permanent URLs or AWS credentials. The source
recommends "S3 multipart upload and restricted, short-lived presigned URLs" and also describes an
API-staged upload flow for the existing product.

## Decision

**Uploads**

1. `POST upload-sessions` authenticates/authorizes, validates size/content type/quota, creates the
   `files` row (`pending_upload`) and the S3 multipart upload under a generated key `f/{fileId}`.
2. The server returns presigned `UploadPart` URLs (≤15 min, exact key + upload ID + part number).
   Objects < 64 MiB use a single presigned `PutObject` with a fixed `Content-Length` and
   `Content-Type`.
3. The client uploads parts directly to S3.
4. `complete` lists parts, completes the multipart upload, then `HeadObject` verifies existence,
   exact size, content type, and optional checksum before transitioning to `processing`/`available`.
5. The key is generated by us; the original filename is metadata only. Overwrite is impossible
   because the key is new and `If-None-Match: *` is not used for multipart (new upload ID).
6. An optional API-proxied path stages ≤100 MiB objects under `staging/`, then server-side copies
   to the final key and deletes the staging object (covers §15.5 where the consumer cannot reach
   S3).

**Downloads**

All downloads stream through the API (`GetObject` → response), never via presigned GET URLs.
Portal/private/public downloads use a 120-second, single-use grant token; integration downloads
use the authenticated content endpoint.

## Consequences

- Fulfils "count only completed downloads", immediate revocation, per-request authorization,
  audit, and range support. API egress is a real cost (see cost model) and a scaling consideration;
  the API streams without buffering.
- S3 CORS must allow `PUT` from the portal origin, with `Content-Type` only.
- Orphaned multipart uploads are cleaned by lifecycle (7 days) and by the worker (24 h).
- Presigned GET can be added later only with a revised counting model (ADR required).
- Local development uses LocalStack 3.8 for S3 (D-29); production uses AWS S3. The adapter is
  endpoint-configurable, so any S3-compatible backend can be used.

## Alternatives considered

- Proxy all uploads through the API: rejected (memory, timeouts, 5 GiB).
- Presigned GET downloads: rejected (cannot count completion or revoke mid-flight; URL may leak).
- Public bucket/CloudFront signed URLs: rejected (violates private storage and audit requirements).
