# Decision Log

Product- and delivery-level decisions made while turning the source specification into a
buildable plan. Architectural decisions have full ADRs under `docs/02-architecture/adr/`.
Status values: **Accepted**, **Provisional** (until stakeholder confirms), **Superseded**.

| ID | Decision | Rationale | Status | ADR |
|---|---|---|---|---|
| D-01 | One Microsoft Entra tenant per deployment; `tid` from configuration, not per request. | v1 is a single-enterprise product. Per-request tenants would add tenancy columns and policy complexity with no current customer. Confirmed by the owner on 2026-10-24. | Accepted | ADR-0004 |
| D-02 | All primary keys are UUIDv7 (`uuid` in Postgres, generated by `uuidv7()` in PG18). | Time-ordered, index-friendly, non-guessable-enough, no sequences to coordinate. | Accepted | ADR-0002 |
| D-03 | Download links use a 256-bit random token (base64url, 43 chars); public links additionally require an 8-char key. | Token is the unguessable locator; the key is a second factor per spec. 256-bit tokens make enumeration infeasible. | Accepted | ADR-0005 |
| D-04 | Link keys are stored as Argon2id verifiers (19 MiB, t=2, p=1) with a server-side pepper. Machine identities use **only Entra client credentials**; Files does not issue API keys in v1. | Low-entropy human-typed key needs a slow hash; Entra avoids a second machine-credential lifecycle. | Accepted | ADR-0005 / ADR-0004 |
| D-05 | Downloads are streamed through the API; presigned S3 GET URLs are not used in v1. | Required to count only completed downloads, enforce per-request authorization after issuance, audit, and support range requests consistently. Trade-off: API egress. | Accepted | ADR-0003 |
| D-06 | `successful_download_count` increments only when the response stream completes. A grant reserves a slot for 120 s; reservation is released on failure. Max-download limits count reservations. | Satisfies §12 (no count on URL generation) and makes concurrency deterministic. | Accepted | ADR-0005 |
| D-07 | **All uploads are proxied through the Files API in fixed-size chunks.** The API writes chunks to a local staging directory on the EC2 EBS volume, verifies them, then uploads the assembled file to S3 using server-side multipart. No client receives presigned S3 URLs. | S3 must be reachable **only** by Files (D-30); a single EC2 still supports 5 GiB through chunked HTTP. The staging file also allows retrying the S3 commit without re-uploading from the client. | Accepted | ADR-0003 |
| D-08 | Human retention: **30 days default** (admin-configurable for new files), **365 days absolute maximum** (no admin exception), user may extend up to 365 only with a mandatory reason note; indefinite **not** allowed. Integration files: indefinite. | Aligns with the owner's policy; the note makes longer retention auditable without allowing exceptions beyond 365. | Accepted | ADR-0006 |
| D-09 | The Microsoft 365 mailbox is configured with POP for receiving, but notifications are **sent via SMTP AUTH** to `smtp.office365.com:587` (STARTTLS) using that mailbox. Graph `sendMail` remains an optional adapter. | POP3/IMAP are receive-only; SMTP AUTH is the send path for the approved mailbox. Avoids a second provider. | Accepted | ADR-0009 |
| D-10 | Backend is a modular monolith (API) plus a separate worker process, sharing the domain/application libraries. Background work uses Quartz.NET (in-memory scheduler) with PostgreSQL advisory locks to guarantee single execution, plus a transactional outbox. No Quartz tables. | Container-first, low ops overhead; worker can scale independently; advisory locks avoid duplicate job execution across replicas without another schema. | Accepted | ADR-0007 |
| D-11 | Frontend is Angular (standalone components) with Bootstrap 5.3 and `@azure/msal-angular`, with **Spanish/English** UI and a language selector (Spanish default). No custom design system in v1. | Matches §16; bilingual requirement; accessible defaults. | Accepted | ADR-0013 |
| D-12 | Rate limiting is hybrid: ASP.NET Core rate limiter at the edge for coarse per-IP/per-integration limits, plus Postgres-backed atomic counters for download-key attempts and lockouts that must survive multiple replicas. | Correctness for the abuse-critical path without adding Redis in v1. | Accepted | ADR-0011 |
| D-13 | **Initial hosting is a single pre-existing Ubuntu 24.04 LTS x86_64 host (≥2 vCPU / 8 GiB, public IP) in `us-east-1`, running Docker Compose with Caddy, the API, the worker, PostgreSQL 18, and ClamAV**, plus one private S3 bucket that already exists. No ALB, ECS, RDS, ECR, NAT gateway, or CloudWatch. Managed services are a later scale-up path. | The construction phase has one machine and one bucket; this minimizes cost and operational surface while preserving container-first delivery and S3 exclusivity. | Accepted | ADR-0010 |
| D-14 | Runtime config is environment-variable based; on the host it lives in `/opt/files/.env` (mode `0600`), loaded by Docker Compose and provisioned by the deployment pipeline. S3 access uses a **static access key** stored in `/opt/files/.env` (the host has no instance role; the existing bucket policy restricts access to the host). Local development uses `.env` with LocalStack credentials. | Matches the source's “secrets in environment files” constraint, avoids AWS Secrets Manager in the initial phase, and keeps browser/API separation. | Accepted | ADR-0010 |
| D-15 | Data retention: **audit events 60 months**, **download events 24 months**, notification events 12 months, idempotency records 24 h, deleted-file tombstones 60 months. All configurable. | Supports long-lived audits/investigations; storage reviewed in the cost model. | Accepted | — |
| D-16 | Deletion is logical first, then physical S3 deletion; metadata tombstones remain for audit. Nightly logical database backups in S3 may retain copies for 35 days. | Meets §11 and avoids over-claiming erasure on a single-node deployment. | Accepted | ADR-0008 |
| D-17 | Malware scanning is **enabled** with ClamAV in production; staged files are scanned **before** the S3 commit. Infected files are quarantined, never uploaded, and never downloadable. Dev/test may disable scanning. | §8 and the owner require scanning; scan-before-commit prevents infected objects in S3. | Accepted | ADR-0003 |
| D-18 | Search uses PostgreSQL (`pg_trgm` + `ILIKE`) with cursor pagination; no external search engine in v1. | Dataset size (10k–100k files) does not justify Elasticsearch/OpenSearch; keeps ops simple. | Accepted | ADR-0002 |
| D-19 | Portal administrators manage metadata, retention, legal hold, and deletion, but **never** get file-content access. Content access requires ownership or an explicit link/ACL. | Least privilege; OQ-05 resolved. | Accepted | ADR-0012 |
| D-20 | **API keys are not used in v1.** The format is retained only as historical context; machine authentication is Entra client credentials exclusively. | OQ-11 resolved on 2026-10-23; superseded by D-42 on 2026-10-27. | Superseded (by D-42) | ADR-0004 |
| D-21 | Owner downloads count toward `files.successful_download_count`; `download_events.source` distinguishes `owner`, `private_link`, `public_link`, `integration`. | Consistent statistics; details preserved for analysis. | Accepted | ADR-0005 |
| D-22 | Content type is set by the server at upload-session creation from a permitted allowlist and enforced on completion; optional magic-byte sniffing is a SHOULD, not a v1 blocker. | Clients can lie; the allowlist + scan gate covers the main risk. | Accepted | ADR-0003 |
| D-23 | Idempotency keys are scoped per integration, retained 24 h, and reject reuse with a different request hash (422). | Standard, safe retry semantics. | Accepted | ADR-0007 |

| D-30 | **S3 is exclusive to Files.** Only the API/worker, authenticating with the static access key in `/opt/files/.env`, may perform object, list, and multipart actions. | D-31 | The initial single-node phase accepts reduced resilience: no HA, best-effort 99.5% availability, RPO ≤24 h (nightly `pg_dump` to S3), RTO ≤4 h. | D-32 | Caddy is the only public listener (80/443) and terminates TLS; the API binds to the private Docker network/localhost, PostgreSQL has no host port, and SSH is restricted to the administrator (enforced by the host's externally managed firewall). A static public IP keeps the address stable. | A public IP is unavoidable with one host, so the exposed surface must be minimized. | Accepted | ADR-0010 |
| D-33 | Backups are nightly logical PostgreSQL dumps written by a Files-owned host script to `s3://<bucket>/backups/`, retained 35 days via lifecycle. No PITR or WAL archiving in the initial phase. | Only EC2 and S3 are available; logical dumps are simple to verify and restore. | Accepted | ADR-0008 |
| D-34 | Production is published at **`files.sacservices.cloud`**; DNS stays at Network Solutions and an `A` record points to the host's public IP. Caddy obtains/renews TLS via Let's Encrypt. | The domain is owned externally; no Route 53/ACM dependency. | Accepted | ADR-0010 |
| D-35 | Malware scanning is **enabled** with a ClamAV container on the host. Staged files are scanned **before** the S3 commit; infected files are quarantined and never uploaded. The production host should be ≥8 GiB (`t3.large`-class) to fit ClamAV + PostgreSQL + API/worker. | Scanning before S3 avoids storing malware; ClamAV memory makes smaller hosts risky. | Accepted | ADR-0003 |
| D-36 | The host and its network/firewall already exist and are managed outside this repo; no VPC/NAT is created by Files. | Matches the available account setup and avoids network cost/complexity. | Accepted | ADR-0010 |
| D-41 | **Entra ID authenticates humans only.** It provides identity (`tid`, `oid`, email) and the delegated `Files.Access` scope; it does not supply app roles, machine credentials, or directory data. | D-42 | **Integrations authenticate with Files-issued API keys** (256-bit secret, prefix + hash at rest, scopes, expiry, revocation, optional IP allowlist; shown once). The `download_link_acl`/`allow_all_tenant` columns are reserved for a future release. | Owner decision 2026-10-27: no Graph, no private links now. | Accepted | ADR-0014 / ADR-0005 |

## Conventions derived from these decisions

- Identifiers exposed by the API are UUIDv7 strings; internal numeric IDs do not exist.
- Enumerations are stored as `text` + `CHECK` constraints (not native PG enums) to keep
  migrations cheap and values readable.
- All tables carry `created_at`/`updated_at`; mutable tables carry a `version` integer for
  optimistic concurrency and ETags.
- Soft-delete columns (`deleted_at`) exist only on `files` and `integrations`; other
  entities are hard-deleted or revoked.
