# Decision Log

Product- and delivery-level decisions made while turning the source specification into a
buildable plan. Architectural decisions have full ADRs under `docs/02-architecture/adr/`.
Status values: **Accepted**, **Provisional** (until stakeholder confirms), **Superseded**.

| ID | Decision | Rationale | Status | ADR |
|---|---|---|---|---|
| D-01 | One Microsoft Entra tenant per deployment; `tid` from configuration, not per request. | v1 is a single-enterprise product. Per-request tenants would add tenancy columns and policy complexity with no current customer. | Provisional | ADR-0004 |
| D-02 | All primary keys are UUIDv7 (`uuid` in Postgres, generated by `uuidv7()` in PG18). | Time-ordered, index-friendly, non-guessable-enough, no sequences to coordinate. | Accepted | ADR-0002 |
| D-03 | Download links use a 256-bit random token (base64url, 43 chars); public links additionally require an 8-char key. | Token is the unguessable locator; the key is a second factor per spec. 256-bit tokens make enumeration infeasible. | Accepted | ADR-0005 |
| D-04 | Link keys are stored as Argon2id verifiers (19 MiB, t=2, p=1) with a server-side pepper; API keys (256-bit) use HMAC-SHA256 with a server pepper. | Low-entropy human-typed key needs a slow hash; high-entropy machine key does not benefit from Argon2 and needs fast lookup/verification. | Accepted | ADR-0005 |
| D-05 | Downloads are streamed through the API; presigned S3 GET URLs are not used in v1. | Required to count only completed downloads, enforce per-request authorization after issuance, audit, and support range requests consistently. Trade-off: API egress. | Accepted | ADR-0003 |
| D-06 | `successful_download_count` increments only when the response stream completes. A grant reserves a slot for 120 s; reservation is released on failure. Max-download limits count reservations. | Satisfies §12 (no count on URL generation) and makes concurrency deterministic. | Accepted | ADR-0005 |
| D-07 | **All uploads are proxied through the Files API in fixed-size chunks.** The API writes chunks to a local staging directory on the EC2 EBS volume, verifies them, then uploads the assembled file to S3 using server-side multipart. No client receives presigned S3 URLs. | S3 must be reachable **only** by Files (D-30); a single EC2 still supports 5 GiB through chunked HTTP. The staging file also allows retrying the S3 commit without re-uploading from the client. | Accepted | ADR-0003 |
| D-08 | Human defaults: retention 365 days, max 3650 days, user override allowed, indefinite **not** allowed. Integration files: indefinite with null expiry. | Conservative defaults aligned with §9/§5.4; all values configurable. | Provisional | ADR-0006 |
| D-09 | The Microsoft 365 mailbox is configured with POP for receiving, but notifications are **sent via SMTP AUTH** to `smtp.office365.com:587` (STARTTLS) using that mailbox. Graph `sendMail` remains an optional adapter. | POP3/IMAP are receive-only; SMTP AUTH is the send path for the approved mailbox. Avoids a second provider. | Accepted | ADR-0009 |
| D-10 | Backend is a modular monolith (API) plus a separate worker process, sharing the domain/application libraries. Background work uses Quartz.NET (in-memory scheduler) with PostgreSQL advisory locks to guarantee single execution, plus a transactional outbox. No Quartz tables. | Container-first, low ops overhead; worker can scale independently; advisory locks avoid duplicate job execution across replicas without another schema. | Accepted | ADR-0007 |
| D-11 | Frontend is Angular (standalone components) with Bootstrap 5.3 and `@azure/msal-angular`. No custom design system in v1. | Matches §16; fast delivery; accessible defaults. | Accepted | ADR-0013 |
| D-12 | Rate limiting is hybrid: ASP.NET Core rate limiter at the edge for coarse per-IP/per-integration limits, plus Postgres-backed atomic counters for download-key attempts and lockouts that must survive multiple replicas. | Correctness for the abuse-critical path without adding Redis in v1. | Accepted | ADR-0011 |
| D-13 | **Initial hosting is a single EC2 instance (Ubuntu 24.04 LTS, x86_64, Elastic IP) in `us-east-1`, on the account's default VPC/public subnet, running Docker Compose with Caddy, the API, the worker, PostgreSQL 18, and ClamAV**, plus one private S3 bucket. No ALB, ECS, RDS, ECR, NAT gateway, or CloudWatch. Managed services are a later scale-up path. | The construction phase has one machine and one bucket; this minimizes cost and operational surface while preserving container-first delivery and S3 exclusivity. | Accepted | ADR-0010 |
| D-14 | Runtime config is environment-variable based; on the EC2 host it lives in `/opt/files/.env` (mode `0600`), loaded by Docker Compose and provisioned by the deployment pipeline. S3 access uses the EC2 instance role, never static keys. Local development uses `.env`. | Matches the source's “secrets in environment files” constraint, avoids AWS Secrets Manager in the initial phase, and keeps browser/API separation. | Accepted | ADR-0010 |
| D-15 | Data retention: audit events 24 months, download events 12 months, notification events 12 months, idempotency records 24 h, deleted-file tombstones 24 months. All configurable. | Supports audits and abuse investigation without unbounded growth. | Provisional | — |
| D-16 | Deletion is logical first, then physical S3 deletion; metadata tombstones remain for audit. Nightly logical database backups in S3 may retain copies for 35 days. | Meets §11 and avoids over-claiming erasure on a single-node deployment. | Accepted | ADR-0008 |
| D-17 | Malware scanning is pluggable; production enables a ClamAV-based scanner, dev/test default to `not_scanned` and allow downloads. Infected files are quarantined and never downloadable. | §8 requires "when scanning is enabled"; optional in v1 but wired end to end. | Provisional | — |
| D-18 | Search uses PostgreSQL (`pg_trgm` + `ILIKE`) with cursor pagination; no external search engine in v1. | Dataset size (10k–100k files) does not justify Elasticsearch/OpenSearch; keeps ops simple. | Accepted | ADR-0002 |
| D-19 | Portal administrators can manage metadata, retention, and deletion, but do **not** get file-content access by default. Content access requires owner or an explicit link. | Least privilege; support access can be added later as audited break-glass. | Provisional (OQ-05) | ADR-0012 |
| D-20 | API key format: `flk_<kid>_<secret>`; `kid` is 12 chars (lookup index), `secret` is 43 chars base64url (32 bytes). | Allows O(1) lookup by `kid`, avoids comparing every key, keeps prefix detectable for secret scanning. | Accepted | ADR-0004 |
| D-21 | Owner downloads count toward `files.successful_download_count`; `download_events.source` distinguishes `owner`, `private_link`, `public_link`, `integration`. | Consistent statistics; details preserved for analysis. | Accepted | ADR-0005 |
| D-22 | Content type is set by the server at upload-session creation from a permitted allowlist and enforced on completion; optional magic-byte sniffing is a SHOULD, not a v1 blocker. | Clients can lie; the allowlist + scan gate covers the main risk. | Accepted | ADR-0003 |
| D-23 | Idempotency keys are scoped per integration, retained 24 h, and reject reuse with a different request hash (422). | Standard, safe retry semantics. | Accepted | ADR-0007 |
| D-24 | All DB timestamps are `timestamptz` stored in UTC; APIs emit ISO 8601 with `Z`; the UI localizes. | Unambiguous expiry and notification logic. | Accepted | ADR-0002 |
| D-25 | Expiration notifications are sent only for human-owned files (integrations own their retention; admins get no per-file expiry emails). | Integration files are indefinite by default; emailing enterprise apps is out of scope. | Provisional | — |
| D-26 | 5 GiB default file limit; 16 MiB client chunk; 64 MiB S3 part; 10,000 chunks max; upload session TTL 60 min, renewable; staging reserve 10 GiB. | Fits 5 GiB in 320 client chunks and 80 S3 parts; bounds memory and disk per session on one EC2. | Accepted | ADR-0003 |
| D-27 | API base path `/v1`; breaking changes require `/v2`; additive changes allowed. | Explicit versioning per §14. | Accepted | ADR-0012 |
| D-28 | A user may create at most 100 active links per file and 1,000 active links per user (configurable). | Abuse and quota control. | Provisional | — |
| D-29 | Local development uses **LocalStack 3.8** (pinned) for S3 because the MinIO Docker images are no longer publicly pullable; production remains AWS S3 and the storage adapter stays S3-compatible. | Keeps the local stack reproducible without a license; any S3-compatible endpoint still works via `S3__ServiceUrl`. | Accepted | ADR-0003 |
| D-30 | **S3 is exclusive to Files.** Only the EC2 instance role used by the API/worker may perform object, list, and multipart actions. The bucket policy denies those actions to every other principal; no presigned URLs are issued; no browser, integration, or human accesses S3 directly. Infrastructure automation may manage bucket configuration but not object data. | The source requires a private bucket and the product must be the only repository client; eliminating presigned URLs removes a whole class of exposure. | Accepted | ADR-0003 |
| D-31 | The initial single-node phase accepts reduced resilience: no HA, best-effort 99.5% availability, RPO ≤24 h (nightly `pg_dump` to S3), RTO ≤4 h. These targets improve when the deployment moves to managed services. | One EC2 and one bucket cannot honestly promise 99.9% or 15-minute RPO; documenting the trade-off is required. | Accepted | ADR-0010 |
| D-32 | Caddy is the only public listener (80/443) and terminates TLS; the API binds to the private Docker network/localhost, PostgreSQL has no host port, and SSH is restricted to `admin_cidr`. An Elastic IP keeps the address stable. | A public IP is unavoidable with one EC2, so the exposed surface must be minimized. | Accepted | ADR-0010 |
| D-33 | Backups are nightly logical PostgreSQL dumps written by a Files-owned host script to `s3://<bucket>/backups/`, retained 35 days via lifecycle. No PITR or WAL archiving in the initial phase. | Only EC2 and S3 are available; logical dumps are simple to verify and restore. | Accepted | ADR-0008 |
| D-34 | Production is published at **`files.sacservices.cloud`**; DNS stays at Network Solutions and an `A` record points to the Elastic IP. Caddy obtains/renews TLS via Let's Encrypt. | The domain is owned externally; no Route 53/ACM dependency. | Accepted | ADR-0010 |
| D-35 | Malware scanning is **enabled** with a ClamAV container on the EC2 host. Staged files are scanned **before** the S3 commit; infected files are quarantined and never uploaded. The production instance should be `t3.large` (8 GiB) to fit ClamAV + PostgreSQL + API/worker. | Scanning before S3 avoids storing malware; ClamAV memory makes `t3.medium` risky. | Accepted | ADR-0003 |
| D-36 | The default VPC and its first public subnet are used; no custom VPC/NAT is created. Terraform still accepts an existing `vpc_id`/`subnet_id` for migration. | Matches the available account setup and avoids network cost/complexity. | Accepted | ADR-0010 |

## Conventions derived from these decisions

- Identifiers exposed by the API are UUIDv7 strings; internal numeric IDs do not exist.
- Enumerations are stored as `text` + `CHECK` constraints (not native PG enums) to keep
  migrations cheap and values readable.
- All tables carry `created_at`/`updated_at`; mutable tables carry a `version` integer for
  optimistic concurrency and ETags.
- Soft-delete columns (`deleted_at`) exist only on `files` and `integrations`; other
  entities are hard-deleted or revoked.
